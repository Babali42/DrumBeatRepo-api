# DrumBeatRepo API (WIP)

## An API to submit beats to drumbeatrepo

## Why this api ?

www.drumbeatrepo.com aims to be a **beat library**.
Then it need to be something people can contribute to.

But I did not get any PR to contribute to the beat database for now.
Beat comes from me or friends of mine.

I think it's too hard for musician to git clone and tutti quanti.
Musician likes to do music isn't it ?

My idea here is to create an api which will be connected to a beat form (non existing yet) on drumbeatrepo
The api will transform it and prepare it for me and send it by email in a `.zip`.

## Why scala ?

I like this language !
As I am a beginner in scala every feedback is welcome.
Especially those about security.

## What is a beat ?

It's mainly a litlle musical pattern which can be represented as a `.mid` file or as a `.json` file.
It can contains samples like `.mp3` or `.wav`.

## Stack

- Scala 3 / Http4s / Cats Effect

## Run locally

```bash
sbt run

curl http://localhost:8080/health
// ok
```
## Docker

Build and run the Docker image using sbt-native-packager:

```bash
sbt docker:publishLocal

docker run -p 8080:8080 api:latest
```

# Documentation for dev
## Scala hexagonale architecture (generated by ChatGPT)

Here’s a compact example of a **Scala backend** using **Cats Effect** with a **minimalistic Hexagonal Architecture** (Ports & Adapters), focused on structure and boundaries rather than implementation details.

---

### Project Structure

```text
src/main/scala/com/example/

  domain/
    User.scala
    UserError.scala

  application/
    ports/
      UserRepository.scala
      EmailService.scala

    services/
      UserRegistration.scala

  infrastructure/
    persistence/
      PostgresUserRepository.scala

    messaging/
      ConsoleEmailService.scala

    http/
      UserRoutes.scala

  bootstrap/
    Main.scala
```

---

### 1. Domain Layer

Pure business concepts.

#### `User.scala`

```scala
final case class UserId(value: String)
final case class Email(value: String)

final case class User(
  id: UserId,
  email: Email
)
```

#### `UserError.scala`

```scala
sealed trait UserError

object UserError {
  case object AlreadyExists extends UserError
  case object InvalidEmail extends UserError
}
```

---

### 2. Application Layer (Ports)

Interfaces the domain depends on.

#### `UserRepository.scala`

```scala
trait UserRepository[F[_]] {

  def findByEmail(email: Email): F[Option[User]]

  def save(user: User): F[Unit]
}
```

#### `EmailService.scala`

```scala
trait EmailService[F[_]] {

  def sendWelcome(email: Email): F[Unit]
}
```

---

### 3. Application Service (Use Case)

Business orchestration.

#### `UserRegistration.scala`

```scala
trait UserRegistration[F[_]] {

  def register(email: String): F[User]
}
```

##### Implementation Signature

```scala
final class LiveUserRegistration[F[_]: MonadThrow](
  repo: UserRepository[F],
  emailService: EmailService[F]
) extends UserRegistration[F]
```

Responsibilities:

* validate email
* check uniqueness
* create user
* persist user
* send welcome email

No HTTP, SQL, JSON, or framework logic here.

---

### 4. Infrastructure Adapters

Concrete implementations of ports.

#### Persistence Adapter

##### `PostgresUserRepository.scala`

```scala
final class PostgresUserRepository[F[_]: Async](
  xa: Transactor[F]
) extends UserRepository[F]
```

---

#### Messaging Adapter

##### `ConsoleEmailService.scala`

```scala
final class ConsoleEmailService[F[_]: Sync]
    extends EmailService[F]
```

---

### 5. HTTP Adapter

Entrypoint adapter.

#### `UserRoutes.scala`

```scala
final class UserRoutes[F[_]: Async](
  registration: UserRegistration[F]
)
```

Possible endpoint:

```text
POST /users
```

The route:

* parses request
* calls use case
* maps errors to HTTP responses

No business rules inside routes.

---

### 6. Bootstrap / Wiring

Composition root.

#### `Main.scala`

```scala
object Main extends IOApp
```

Wiring example:

```scala
repository
  -> application service
  -> routes
  -> http server
```

This is the only place where implementations are chosen.

---

### Dependency Direction

Core rule:

```text
Infrastructure -> Application -> Domain
```

Never:

```text
Domain -> Infrastructure
```

The domain knows nothing about:

* HTTP
* databases
* Cats Effect runtime
* JSON
* Kafka
* Postgres
* external APIs

---

### Minimal Cats Effect Typeclass Usage

Typical constraints:

```scala
MonadThrow   // business logic
Sync         // suspend side effects
Async        // async / networking
Temporal     // retries / time
```

Keep constraints as small as possible.

---

### Typical Request Flow

```text
HTTP Request
    ↓
Route Adapter
    ↓
Application Service
    ↓
Ports
    ↓
Infrastructure Adapters
    ↓
Database / External APIs
```

---

### Minimal Philosophy

A clean Cats Effect hexagonal backend usually aims for:

* pure domain
* effect-polymorphic services
* ports as traits
* thin adapters
* explicit wiring
* no framework leakage into core logic

The result is:

* testable
* composable
* easy to refactor
* runtime-agnostic
* maintainable at scale


That’s enough for many production services.
